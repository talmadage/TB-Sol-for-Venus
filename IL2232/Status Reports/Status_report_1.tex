\section{Problems / Action plan}
\subsection{ProGram Tool Malfunction}
\begin{itemize}
    \item \textbf{Problem:} The ProGram compiler, which is intended for generating the bit-serial CISC-V processor, is still not functioning properly. Compilation fails due to unresolved external dependencies and library conflicts that originated from the legacy codebase. However, since the current phase of the project does not yet require the use of ProGram for any active module, this issue has been assigned a lower resolution priority.
    
    \item \textbf{Action plan:} Paul will continue to investigate potential fixes based on the supervisor’s recommendations. The current plan is to remove unnecessary external references and rebuild the tool environment to isolate the error. If these actions do not resolve the issue, the team will formally request assistance from the supervisor to ensure the tool can be restored before the CISC-V implementation phase begins.
\end{itemize}

\subsection{Simulation-Only Testbench}
\begin{itemize}
    \item \textbf{Problem:} The current testbench is only compatible with simulation because its verification method relies on printing execution logs and comparing them against a trusted RISC-V simulator (currently Spike). This approach involves frequent file I/O operations and therefore cannot be synthesized or deployed directly on FPGA hardware, which conflicts with the project’s final goal of on-board verification.
    
    \item \textbf{Action plan 1:} The immediate plan is to complete the current simulation workflow using QuestaSim to verify processor correctness. This phase also includes finalizing the log-printing functionality for the Spike simulator, which is nearly completed by Xiaotian.
    \item \textbf{Action plan 2:} For FPGA-based validation, a new approach will be adopted using the RISC-V test suite. This test method verifies correctness by checking whether a specific register returns zero at the end of execution, allowing the binary to be uploaded into FPGA SRAM for self-contained verification without logs—thus making it fully synthesizable. This task will be jointly handled by Xinxin and Chongnan.
    \item \textbf{Action plan 3:} If, however, the supervisor confirms that on-board log comparison is still required, the alternative plan is to transfer the golden log to the FPGA and perform comparison directly in hardware. This contingency option will also be developed by Xinxin and Chongnan if needed.
\end{itemize}
\subsection{Limited FPGA I/O for Dual-Board Integration}
\begin{itemize}
    \item \textbf{Problem:} The number of available I/O pins between the verification FPGA and the processor FPGA is insufficient to support the current parallel signal interfaces used by the testbench and processor modules. This limitation was anticipated early in the project, and the team has prepared an appropriate workaround.
    
    \item \textbf{Action plan:} The solution is to design and implement a bit-serial communication module on the verification FPGA, which will serialize address, data, and control signals—transmitting them bit by bit instead of as 32-bit parallel buses. This module will act as an intermediary, ensuring complete communication between the testbench and the processor within the physical I/O limits of the hardware. Paul, Lorenzo, and Chinmay are jointly responsible for the design and implementation of this module.
\end{itemize}

\subsection{Risks to Be Reported}

According to the latest risk matrix evaluation, four risks are currently considered as really critical for the project (in the red zone) and should have a higher attention.

\subsubsection*{Risk 3 – Extreme Environment}
The SoI CMOS technology used in this project may not be enough for the environmental conditions of Venus. If it’s the case, the final demonstration may not be really representative of the objective and it would limit the scientific value of the prototype. We should keep in mind this while creating the testbench to imagine a way to simulate as closely as possible the Venus environmental conditions.

\subsubsection*{Risk 2 – Multi-FPGA System Complexity}
The project requires two FPGAs, one for the processor and one for the testbench, communicating through a custom interface. We haven’t done this communication interface yet but it might be the most challenging part of the project. Synchronization, timing management, and debugging of this inter-FPGA are difficult and could lead to delay in the final validation phase. That is why we have allocated several springs for this task.

\subsubsection*{Risk 6 – Verification Coverage}
The testbench might not generate a sufficiently diverse set of test scenarios to achieve full verification coverage. A lot of special cases should be taken care of and an incomplete verification may allow hidden functional bugs. Discovering those bugs in the late stages of the project could impact the demonstration reliability. As a result, we will try to expand the testbench with randomized and stress testing sequences.

\subsubsection*{Risk 11 – Integration Timeline Underestimation}
Multi-FPGA integration may take longer than expected. This phase depends on several things: synthesis, communication debugging, and testbench validation. Those delays could compress the verification phase and result in a rushed testing, which is never good in a project. It’s important to have a structured plan with clear milestones, define a “minimum viable demo” to ensure at least one stable version at the end and allocate additional buffer time in the coming sprints to focus on debugging and hardware validation.

\section{Project changes from the project plan}

Since the initial project plan was submitted, several adjustments have been made to the project's organization, prerequisites, and documentation to better align with practical realities and emerging challenges.

\subsection{Changed Requirements}
The core project requirements have remained largely stable. The primary objective continues to be the implementation and validation of a testbench system for both the RISC-V and CISC-V (bit-serial) processors. No significant changes to the functional requirements or deliverables have been necessary.

\subsection{Changed Organization}
Several organizational improvements have been implemented to enhance project flexibility and team coordination:

\begin{itemize}
    \item \textbf{Agile workflow adoption:} The team has fully embraced an agile methodology to maintain flexibility and quickly adapt to new findings or technical challenges that emerge during development.
    
    \item \textbf{Weekly sprint-based planning:} The project now operates on a structured weekly sprint cycle, with clear short-term goals defined at the beginning of each sprint to ensure continuous and measurable progress.
    
    \item \textbf{Iterative development approach:} Rather than following a rigid sequential process, the team now emphasizes iterative improvements and early validation, allowing for faster identification and resolution of issues.
    
    \item \textbf{Regular supervisor engagement:} Weekly meetings with supervisor Johnny Öberg have been established for sprint reviews, live demonstrations of progress, and short retrospectives to discuss improvements and address blockers.
\end{itemize}

\subsection{Changed Prerequisites}
Several technical challenges were encountered that required adjustments to the project's initial assumptions:

\begin{itemize}
    \item \textbf{ProGram compiler errors:} Compiler errors were discovered in the provided ProGram tool. These errors were identified early in the project, allowing the team to develop workarounds and avoid a complete project blockage.
    
    \item \textbf{FPGA board connectivity issues:} The FPGA boards were initially not functioning correctly due to faulty cables. These hardware issues were detected early and resolved before the system integration phase, preventing delays in testing.
    
    \item \textbf{Complex software setup:} Installation and configuration of the development environment on personal computers proved more complex than initially anticipated, requiring additional time and documentation.
    
    \item \textbf{Power adapter compatibility:} US power cables were incompatible with local power outlets. Proper adapters were quickly procured through established contacts, minimizing downtime.
\end{itemize}

\subsection{New Documents}
To improve project organization and knowledge transfer, the following documentation has been created beyond the original plan:

\begin{itemize}
    \item \textbf{Project management document:} A comprehensive document detailing the team's agile processes, sprint workflows, and decision-making procedures.
    
    \item \textbf{Detailed README file:} An extensive README has been written to document the codebase structure, setup procedures, usage instructions, and troubleshooting guidelines for future development and maintenance.
\end{itemize}
